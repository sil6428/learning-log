# 2026-08-01 - Set up T3MP3ST with a local Ollama model

## Session

- **Area:** Local AI, Windows systems, cybersecurity lab setup, and dependency security
- **Goal:** Run T3MP3ST locally without a hosted API key and understand its resource and security tradeoffs.

## Work completed

- Verified the system has a 12th-generation Intel Core i7-1260P, 15.7 GB of RAM, and Intel Iris Xe integrated graphics.
- Installed and verified Ollama for Windows, then pulled the 4-bit `llama3.2:3b` model.
- Cloned the T3MP3ST source, installed its Node.js dependencies, and completed a TypeScript production build.
- Configured T3MP3ST to use Ollama's local API and saved `llama3.2:3b` as the default model.
- Started the War Room on the loopback-only address `127.0.0.1:3333`.
- Confirmed that the health endpoint reported the server as operational and the local LLM as connected.
- Sent a harmless test prompt through T3MP3ST's own local-model adapter and received the expected response.
- Unloaded the model after testing so Ollama would release its working memory until the next request.

## What I learned

- T3MP3ST is an orchestration and security-testing framework, not an Ollama model. Ollama supplies the reasoning model behind the framework.
- A browser action travels through the local Express API, the T3MP3ST LLM adapter, and Ollama's `/api/chat` endpoint before the answer or proposed tool call returns to the interface.
- Parameter count does not equal runtime memory directly. Quantization reduces model weight size, while context length, inference buffers, and application overhead add memory beyond the downloaded file.
- On this 16 GB system, a 3B model is workable but still leaves little headroom when other applications already consume most of the RAM. A 7B or 8B model would be much more likely to page to disk.
- Binding the War Room to `127.0.0.1` matters because its API can execute approved tools. It should not be exposed to a LAN or the public internet without authentication and a properly configured reverse proxy.
- Authorized scope and rules of engagement must be defined before any active testing.

## Problem encountered

- PowerShell's script-execution policy blocked the `npm.ps1` shim, so the Windows executable shim `npm.cmd` was used instead.
- T3MP3ST's doctor script reported several installed Windows commands as missing because its command detection expects Unix-style tooling.
- The CLI connection-test path incorrectly required an API key for the keyless local provider, so the underlying T3MP3ST adapter was tested directly.
- `npm audit` reported two high-severity transitive dependency findings: vulnerable `brace-expansion` versions reached through ESLint tooling and a vulnerable `postcss` version reached through Vitest and Vite. No forced dependency rewrite was applied.
