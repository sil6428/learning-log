## What I learned

- IAM review is more useful when each heuristic explains its likely impact, remediation, and false-positive boundary instead of only printing a warning label.
- GitHub Actions OIDC trust should constrain both the token audience and the repository, branch, tag, or environment represented by the subject claim.
- An `Allow` statement containing `iam:PassRole` with a wildcard resource can enable privilege escalation even when the rest of a policy looks narrow.
- Cryptographic building blocks do not automatically make a production-safe messenger. Forward secrecy, key rotation, endpoint verification, NAT behavior, and independent review must remain explicit limitations.
- Measured project claims are easiest to defend when the README, tests, resume, portfolio, and repository history all describe the same implemented boundary.
